Automatic Golden Updates

A tool that refreshes reference files for UI automation tests after an intentional product change, in a loop, until nothing fails.

Where Siemens EDA, Platform Framework teamRole InternStack Python, Jenkins, Git, SeleniumStatus Proof of concept

The problem

UI automation tests compare their output (PNG, PDF and DXF files) against stored "golden" reference files. When a product change is intentional, those comparisons fail and the goldens have to be refreshed.

A platform change such as a Java version upgrade can affect around 300 tests and 500 files. The framework stops a test at its first failing comparison, so each run exposes only one bad golden per test. A test with N bad goldens needs up to N runs, and each run takes several hours. By hand, that takes days.

The loop

  1. Sparse clone. Clone only the updater and the folders of the listed tests, and remove the clone at the end.
  2. Submit. Start the test run on Jenkins and find the triggered build.
  3. Wait. Read the submission ID and poll the run status until it completes.
  4. Read failures. Collect the failing tests from the results site.
  5. Update goldens. For each failed comparison, find the golden and the actual output in the result log, download the actual output and replace the golden. PNG, PDF and DXF are each handled.
  6. Commit and push. Commit the changed files to the branch, with one rebase retry.
  7. Repeat. Re-run only the tests that still fail.

When it stops

  • No failures remain: success.
  • The iteration cap is reached (18 by default): it lists what's left.
  • Nothing could be updated in two consecutive runs: the failures are probably not golden-related, but an infrastructure problem, a crash, a timeout or a product defect.
  • The submission build fails or the run status is unknown: it stops with a link to the build.

Without the commit option it does a dry run: it submits and reports failures but changes nothing. A small desktop front end shows run history and a dry-run switch.

What's been verified

  • Submit, wait, status polling and failure listing on a real run of about 5.5 hours and 9 tests.
  • PNG updates on a real run, and sparse clone, commit and push against a real repository.
  • PDF and DXF update logic offline, against sample result logs.
  • A full multi-run loop that reaches zero failures is not yet demonstrated.

Limitations and next steps

  • It needs a personal access token and runs from a desktop. The next step is a parameterised Jenkins job that needs no personal token.
  • It can't tell infrastructure failures from product defects by reading logs. It uses two runs with nothing to update as the signal.
  • Occasionally a submission build fails because a build agent disconnects. Resubmitting fixes it, so automatic retry is planned.

This is a high-level write-up of internal work. The code isn't public, and names, hosts and paths are left out on purpose.
